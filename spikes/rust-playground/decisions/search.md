# Decisions — Item search: the crate, the line, the query, the answer, the basis, the trade boundary

Part of the decision registry (`CONTEXT.md`, "Decisions — the registry"): the rulings that bind item search — the `acquisition-search` crate and its edges, a line's identity, the query tree and its text, occurrence binding, absent against undecided, named totals, the counts view, the realm scope, the vocabulary read, the held corpus and its basis, the trade translation, the answer shape, reach, the limits, what reference data admits, and the one deriver. Read this before touching `search/` or the crate, with `search/README.md` (the slice's working directory, its rules and traps) and `search/DIGEST.md` (the `S` ids cited here, looked up by id and never read whole). Same rules as `CONTEXT.md`: one entry per decision, stable `C<n>` ids never reused, the ruling verbatim, *Why:*, pointers; the mechanism lives in the code's doc comments under the id — and, until code takes each paragraph, the contract detail that decides answers is `search/DESIGN.md`, binding with its line, which each line's builder reads with the line.

**Standing.** Every line is provisional until the owner's first seat at a surface he can use (`brainstorming-notes/23-search-synthesis-plan.md`, decision 15), and may cycle back then — except what he ruled in his own words, quoted on the line or in `search/DESIGN.md`: C89 and C103 whole, C1's amendment (`CONTEXT.md`), C98's revision check before every answer ("by construction", note 28 §4), the harvest's verdicts on C92, C93, C96 and the pseudo classes of C94, C101 and C102, the stage-5 audit's on C105, C106 and C96's "never a term", C107 on the legacy track, and session C's amendments to the reference. Six lines carry a choice one model made, checked for logic by Astra (note 28, last section) and exercised by no user yet, and the seat revisits them first: C91's ambiguity error, C92's binder and sort scalar, C93's undecided route, C95's sum rule, C98's basis as the contract, C104's text adapter. The language on one page, an example per construct, is `search/DESIGN.md`'s reference. ## The crate and the deriver (ruled)

- **C89 — Item search is its own library crate, `acquisition-search`, over the store's read API.** It links the store, and `acquisition-plan` once a query reads the effective price (C81); never the daemon, the client, an HTTP client or an async runtime, and it opens no file of its own, so it is no third door (C12): a frontend links it as it links the planner (C1). The daemon and the planner never link it — a plan takes item ids, never a query. *Why:* each property is an edge the check can refuse, and a search edit recompiles no daemon. Ruled 2026-09-17 (owner: "Agreed with a new crate"; the edges: "I agree to 1 entirely").
- **C103 — One deriver per fact.** Place and every other ingest fact come from the store's read, joined as the store's own reads join them (S131), never re-derived from a body; what a body says is derived in the search crate, by a pure function of the body and those facts that names no store type, so it can move under the store unchanged if persistence fires (C98). What the store gains for it is C108 (`decisions/store.md`). *Why:* two reads in one crate already mean different things by "in this league" (S131); two derivers over one body is that bug with a crate line through it. *Evidence:* S127, S128, S131. *Pinned:* `acquisition-search/tests/derive.rs`. Ruled 2026-09-17 ("I agree to 1 entirely").

## The line and the query

- **C90 — A line's identity is (realm, kind, template), and the displayed text is the only name a line needs.** The template is the displayed English with each number replaced by `#`, markup reduced to its display half and the sign carried in the number; numbers are ordered slots, never averaged. Kind keeps both coordinates the body gives — the source array and the flags the line carries (`crafted`, `fractured`, `mutated`; S17) — so neither bucket rule is chosen silently. A rename is a new line. A stat id exists only at the trade boundary (C99). *Why:* the template names every line and the stat id two thirds (S155); the text is the moving part. *Evidence:* S3, S4, S17, S68, S71. *Pinned:* `acquisition-search/tests/derive.rs`. 2026-09-17.
- **C91 — A query is one typed tree, and a value: immutable, serializable, handed between a human and an agent, to the site and from it.** And, or, not and at-least-N-of (with a lower and an upper bound) compose across every field, line and place alike, and every surface is an encoding of the one tree. A refinement is the old query, parenthesised, and a new term. There are no silent modes: an ambiguity the grammar defines is an error that shows the readings, and everything else follows one visible rule that the canonical query prints back. *Why:* composition the C++ app lacks and the site allows only among stats (S169); an answer that says how it was understood is what both designs reached unprompted. *Evidence:* S169, S172. 2026-09-17.
- **C104 — The text is carried on every seat; the tree is accepted and always returned.** The canonical text and the canonical tree are one value, each printing to the other; the CLI and the MCP pass the text, a client that holds a tree (a GUI's rows) may send it, and every answer carries both. *Why:* both reviewers wrote text in both designs; that the string is the shorter form is a judgment, not a measurement. It departs from the letter of R14 — "a query object, not a text argument" (S195) — and keeps its intent, a refinement being the previous query plus one term. No review compared the text with an equally specified JSON, so this is an adapter choice, the first the owner's seat revisits. *Evidence:* S195. 2026-09-17.
- **C92 — A comparison on a line binds one occurrence; the item's total is asked for by name.** `sum` of the line, or a named total (C94), is the item's sum. Conditions on one line are one term and hold on one occurrence. A ranged line (`# to #`) names its numbers `low` and `high` and admits `avg`; a comparison, sort or sum naming no slot on a line with several is an error that lists them. A row shows the line whole; an item with no qualifying line sorts last; the answer counts the items whose lines reach a lower bound only together. *Why:* a sum is built from occurrences by a word; an occurrence cannot be recovered from a sum. *Evidence:* S27, S28, S47, S68. Owner 2026-09-17: "low and high are better than min and max, and this only applies to ranged modifiers".
- **C93 — Absent is false; undecided is one outcome with a named reason, and the two are never one count.** A comparison on something the item lacks is false, never zero (S158); absence is claimed only when everything that could hold the thing was readable. What cannot be established on an item — an unread body, a base the class table lacks, an unresolved price (C81) — makes only the terms that needed it undecided; composition carries it, and an item undecided at the root is no match, counted apart. Per atomic term the answer counts matched, failed, lacked, undecided. *Why:* an unknown count that is nonzero on every ordinary query stops being read; one that is nearly always zero is read when it is not. *Evidence:* S107, S158. Owner 2026-09-17: "accept".
- **C94 — A named total is a sum that answers, defined once as reviewed reference data (C68).** A row names the contributing line — template, kind, realm, slot — and its weight; a row with a weight and no slot counts the line; a total over ranged lines is a range, summed slot-wise, and takes `low`, `high` and `avg`. Nothing else defines a total, so it has one meaning in every surface; an unreadable contributor leaves a subtotal marked incomplete, never a total, and no recipe for a realm is never a zero. The answer prints a definition on request; a definition is checked against the reference data, loudly, when the table is built. *Why:* a total that may decline failed the everyday question in use (stance 3). *Evidence:* S29, S49, S111. Owner 2026-09-17: "yes, accepted".
- **C95 — The counts view has two shapes and one optional sum; there is no aggregation language.** Several names give independent facets (AQ1) or one crossed table of two fields, never `line` (C97). A count may carry one sum: lacking adds nothing and is counted, empty is zero, unread leaves an incomplete subtotal (C94). Summing raw line projections, combining views, sorting counts, and standalone sums are errors. *Why:* counts and totals (S170, S189) without an aggregation language (S191) or an implicit largest occurrence. *Details:* `acquisition-search/src/counts.rs`, `answer.rs`, `bind.rs`. *Pinned:* `acquisition-search/tests/counts.rs`. 2026-09-17; E2, E4–E5 accepted 2026-09-22 (`SEARCH-SLICE.md`): "ok, agreed"; "For sum, we don't need a grand total."
- **C105 — A count accounts for every matching item.** Known absence is `none`; a key not established is `undecided` (C93), neither omitted nor merged with a value. Every match is in at least one real bucket, `none` or `undecided`; a one-value key's buckets sum exactly to the total. *Why:* inventing a value or dropping an item breaks C93 or the total. *Details:* `acquisition-search/src/counts.rs` (selectors and vocabulary presence, E1 and E3 accepted 2026-09-22; `SEARCH-SLICE.md`, "Holes ruled"). *Pinned:* `acquisition-search/tests/counts.rs`. Owner 2026-09-18: "Undecided in aggregate doesn't have a reason"; "a separate bucket for none"; "I agree with the two invariants".
- **C96 — Place is terms, but the realm is the search's scope, never a term, and a query never spans realms by default.** League, tab, character and container are terms like any other; which realm a search runs over is stated outside the conditions, printed back in every answer, and never hoisted from a branch of the tree. Over a store holding more than one realm, a query naming none is an error that lists them (S199), and an explicit all-realms scope exists. Within a realm the default is every league, live items. The scope block says what was searched: items, realms, leagues, locations never fetched, the oldest fetch. *Why:* a template and a total mean different things in two games (C58). The default is new here and labelled so. *Evidence:* S199. Owner 2026-09-17: "accept".
- **C97 — The vocabulary is a read of this corpus, and it is the same call as search.** Counting by `line` under the query in hand lists the templates the matching items carry, by kind — and by realm under an all-realms scope — ranked by how many items carry each, and the range per slot; several texts may be asked in one call, and every row carries the term that selects it in its realm, ready to paste, source and flag both selectable. The closed lists — fields, kinds, flags, totals with their definitions — are printed in the help. The owner's autocomplete and the agent's schema discovery are this one read. *Why:* S174 and S190 state one need; scoped discovery and the ready fragment were each the other model's reviewer's strongest praise. *Evidence:* S174, S181, S190. 2026-09-17.

## The corpus, the boundary, the answer

- **C98 — No search service: a consumer holds the corpus, and every answer is derived from one consistent basis and labelled with it.** The basis names the store and account, one snapshot of facts and their locations, the intent revision, and the reference and derivation versions; a held corpus is reused only while every component it carries still matches the basis of the answer in hand, checked before every answer. A write after the basis is chosen does not unmake a correctly labelled answer. Nothing is persisted first: a persisted projection is a candidate, never a preselected successor, and waits for a measured failure. *Why:* a check is structure where an event is discipline (P5); a stale result taken for current truth is C48's failure. *Evidence:* S135, S150–S153. 2026-09-17.
- **C99 — Direction. The trade boundary is a translation with a report, in both directions, and the stat id lives only here.** A site URL decodes with no network (S56). Each clause lands as exact, ambiguous, unsupported or listing-only, and a nonempty remainder means the result is never run as equivalent; a clause the published model cannot represent stays in the remainder. The site's bound on a ranged line is its average (S47) and translates to `avg` on the line (C92); an undecided pair is shown with both candidates (S67). A line with no stat id cannot cross (S155). *Why:* the report makes a missing mapping honest; it does not supply one. *Evidence:* S26, S41, S47, S56, S57, S67, S106. 2026-09-17.
- **C100 — One answer shape, whatever was asked: the canonical query, the basis, the scope, the terms block, the total, a view, and how to continue.** A row is compact by default — id, name, base, rarity, place by name and id, and the lines the query touched with their values (the decision view, C53) — and the caller may name fields (S193); the body only through `show` (`--against`: the why-not). Every printed id is accepted back (S198). A continuation names its basis (C98) and the query, view and order it continues, and is refused across a change. `priced` is the effective price the pricing area defines (C81), joined read-only. *Why:* an answer that carries its evidence needs no second call and no body. *Evidence:* S176, S192, S193, S196, S197, S198. 2026-09-17.
- **C101 — A missing reach is a field to add, never a general door.** There is no raw-path accessor over the body and no general collection syntax. Socket colours are asked two ways: over the whole item, and within a link group, where every colour and count named must be met together by one group — any qualifying group (S59). A pseudo that is not a sum or count over lines is a derived field, a named function over properties, lines and reference data (C68), listed with its definition, never a total row (C94). The site's item-reading filters not yet mapped stay an open catalogue (S42), listed as gaps. *Why:* reach is a property of the derivation (stance 6) and a derived field is the cheap class of change (S135). *Evidence:* S16, S22, S42, S58, S59. Owner 2026-09-17: "yes, accepted".
- **C102 — The digest's limits register is inherited, with one stated exception, and each limit is an output.** S12, S14, S52, S53, S67, S107, S111, S177, S178: what the search says on meeting each is the register's wording; the exception is S111 under a shipped total, where a moved template looks like a lacking one (C94). Binding occurrences does not say which twin is local (S52, S72); a site defence bound is inexact (C99); a pseudo needing the mod behind a line is out of reach (S52); judgment — what is good, worth keeping or legacy — is the user's (stance 4, C106). The search never fuzzy-matches, values, judges legacy, fetches, acts on the stash, or recovers the mod behind a line. *Why:* a limit stated at the answer is read; one in a document is not. 2026-09-17.
- **C106 — Reference data admits game data and community convention, never judgment.** Data is what the game files state (base ranges, the mod table); convention is a concept with a published community definition (equipment, the trade site's categories). Both enter under C68 from a registered surface (C79), through the admission test the contract detail states, and remove nothing: the user composes their own meaning from terms. Judgment — what is good, what it is worth, what to keep — is never embedded. Legacy stays the user's (S178, C107). *Why:* C102 gave base defences to the user while C101 built a field on them. *Details:* `search/DESIGN.md`; `class.rs`. *Pinned:* `tests/class.rs`. Owner 2026-09-18: "I approve the proposed three-way line as amended."
- **C107 — Legacy is the user's word; a source's own label may be a field.** No field, term or output of the search says "legacy" (S178, R8). What a registered source prints about an item — the variant label Path of Building gives a unique (`Pre 3.23.0`, `Current`) — is convention under C106 and may back a derived field (C101) that prints the label and the source's version; an item that fits an old and a current variant, or none, is undecided with its reason (C93). *Why:* the measurement found a source for a unique's variants and none, for any kind of item, that says what the game can still produce. *Evidence:* `search/legacy/README.md` at `77bca830`. Owner 2026-09-18: "legacy is not well-defined enough to become a field. Variant is better."

## Parked (do not build yet; each with its trigger)

Scope this area has deferred, with the trigger that reopens it, so deferral never needs re-arguing. A fired trigger deletes its entry in the build's commit; what crosses every area is parked in `CONTEXT.md` instead. An entry is the item, where it lands, and the trigger that reopens it, with at most one clause of why; a workaround is a README known gap, history is git. The triggers were retuned at the harvest on Astra's check (note 28, last section, "Parking lot").

- Saved queries, user names, tags → user-scoped intent through the store (the `user.db` home, `decisions/store.md`, built as the prerequisite). Trigger: the first consumer asking to save, name or tag a query — another kind creating `user.db` is not this trigger. Then: A's version rule and B's composability; the bare-word collision is gone — a bare word is an error that shows its readings (`search/DESIGN.md`), so a name changes no old search. A query is already a value that travels between clients (C91); only the write is parked.
- A persisted projection (A's transactional one is a candidate; direct SQLite for a consumer that does not outlive its query is another, S152) → under the store, the deriver moving with it (C103). Trigger: a measured failure of an agreed response budget — a CLI ask over 500 ms first; the streaming body read and the re-derive under an active refresh are measurements the first build owes, not triggers by their existence. A fired trigger opens the experiment among the candidates, never automatic persistence.
- Whole-corpus export of the derived lines — JSON first; a SQLite file stamped with its basis if JSON in hand is not enough → the search crate's CLI and MCP adapters, as a writer over the derivation's table shape (lines as rows, fields as columns, place by name, S200). Trigger: a recorded question the term language, the counts view and the JSON answer could not serve. An export carries status enough to keep absent and undecided apart (C93) and reads only its own table. *The SQL surface was withdrawn 2026-09-17 (note 23, decision 16); SQL as the engine for a long-lived consumer was declined by measurement (S146–S148); for one that does not outlive its query it stays open (S152, the persistence park).*
- A grouping above class (`category`) → the class table, a convention under C106 (its authority named, the rest corroboration), by reviewed membership and base-name rules, never a dotted prefix (note 31 K7: the 14 parents are unions; seven leaves need base names). Fired at step 6 and kept parked (owner, 2026-09-23: "yes, lets keep this parked"): OQ5 is pinned from his words with the wearable classes spelled out (`SEARCH-SLICE.md`, "Holes ruled", step 6, G6). Trigger: the first seat showing that typing the list bites. *Logic-checked by Astra, used by no one.*
- A tab's type as a field (GGG's `type`: `MapStash`, `QuadStash`, `CurrencyStash`, …) → the binder's place fields, a closed set over what the store's read already hands over with each location (C108, `tab_type`). `tab:` tests a name and never a type, so "everything in a map tab, whatever it is called" cannot be asked. Trigger: the design hardened — the owner's first seat behind it — or a recorded question that needs it, whichever first (owner, 2026-09-20: "so we can add it later once the design is hardened").
- A sticky default realm (the owner's idea, 2026-09-18: "a way to set the realm as a state variable that applies to searches until changed or unset") → the adapters, never the model: a CLI knob, a GUI's dropdown or an MCP default supplies the scope a request omits, and the answer prints it (C96); persisted across sessions it is user-scoped intent (the `user.db` park above). Trigger: the first seat holding two realms that tires of stating the scope. League is the same kind of default (2026-09-19): an adapter may supply it, the answer prints it, its trigger the owner's first seat forgetting it.
- A realm word inside a term (one query with different conditions per realm) → the line selector, beside the kind word. Declined 2026-09-18 ("Disallow realm as a search term", C96): adding it later breaks nothing, removing it would; until then a listed limit whose workaround is two searches. Trigger: a recorded question that needs different conditions per realm in one answer.
- Query by example (the one-item view prints the item as an editable query) → a rendering over C92. Trigger: the first seat that asks. *Reached by neither proposal.*
- A quality-normalised defence field → the derivation (C101). Trigger: a translated trade query with a defence bound in its remainder (C99); until then a listed gap, never counted as reach.
- The totals coverage trial (how many lines containing "Resistance" does `pseudo.total_res` not count, on the real corpus) → one script over the census, run before the first recipe is accepted; a word-based trial measures coverage, not membership. Trigger: stage 6 shipping the first total.
- A unique's variant as a convention-backed derived field (C107, C101) → the derivation: the label Path of Building gives the variant an item's lines fit (`Pre 3.23.0`, `Current`), printed with the clone's commit; an item that fits an old and a current variant, or none, is undecided with its reason (C93). Measured over the owner's store, with what the fit needs — the catalyst rescale, several variants at once on some entries — and what it leaves unmeasured (implicits an entry does not list): `search/legacy/README.md` at `77bca830`. The entries' `Source:` line (`No longer obtainable`) is a second label the same source carries. Trigger: stage 6 reaching OQ2, whose first test is the owner's S165 example.
- Whether a line can still be made — a rare's mod, an enchant, a crucible node → no registered surface on this machine says so (`search/legacy/README.md`, "The sources read"), so the answer is the user's (S178, C107); rares also need mod attribution (the park below). Trigger: the owner procuring a source that dates a line's removal, registered first (C79).
- Mod attribution (which mod made a line: its affix type and tier; the ten site pseudos C102 lists as out of reach) → a derivation over the game data, with the local/global twins (S72) as its first test. Trigger: a recorded question that needs an affix count or a tier.

A restored copy carries its original's id, so the id closes the refetched file and not the copy. Trigger: the first consumer that holds a corpus across asks, or `--next`.

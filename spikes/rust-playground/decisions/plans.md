# Decisions — Intent, plans, apply

Part of the decision registry (`CONTEXT.md`, "Decisions — the registry"): the rulings that bind the sync policy, the planner, plan envelopes, quote, apply and its gates (`acquisition-plan`, `acquisition-store/src/annotations.rs`, the `apply` kind in `daemon.rs`). Read this before touching that code; the cross-cutting decisions and the invariants are in `CONTEXT.md` and are always loaded. Same rules as there: one entry per decision, stable `C<n>` ids never reused, the ruling verbatim, *Why:*, and pointers; the mechanism lives in the code's doc comments under the id.

## Intent, plans, apply

- **C36 — The sync policy is the first annotation: a per-account, inspectable declaration of desired coverage and freshness — not a scheduler — compiled by the frontend-side planner into minimal requests.** `metadata.items` counts are heuristic evidence: they can prove a tab changed, never that it didn't. *Why:* C++ tracked-set/clean-refresh semantics, the old delta/selection topic, and both redesign essays describe this one object. *Pinned:* `acquisition-plan/src/lib.rs` (the count heuristic, the strict parse). Decided 2026-08-31.
- **C37 — A tab id in the sync policy covers that tab and its children.** A map/unique tab's substashes are planned once their stubs are on record — the cycle after the parent's first fetch, binding untouched; a folder's children at once; a stub counting 0 is skipped with a named reason. Type-level filters are parked with a trigger. *Why:* the tracer rung left 64 substashes uncovered under an exact id match, and the owner's intent for a named map tab was its contents. *Details:* `acquisition-plan` doc. Decided 2026-09-01.
- **C39 — The planner lives in `acquisition-plan`** — depends on core + the store, linked by frontends only — and owns policy compilation and Plan construction; the store exposes neutral snapshots, never half a planner. *Why:* keeps "the daemon never reads the store" enforced by the dependency graph, not discipline. *Pinned:* `tools/docs-check.sh` (the edge is refused), `snapshot.rs`. Decided 2026-08-31.
- **C40 — `quote` is its own protocol request: a read-only, non-reserving projection over current daemon knowledge** — observation time, basis, per-policy/per-scope estimates, unknown prerequisites; applying may receive a different schedule. Never a flag on `Submit`. *Pinned:* `daemon.rs` (quote tests), `acquisition-plan/src/lib.rs` (`with_quote`). Decided 2026-08-31.
- **C41 — Reads observe, assertions plan, apply spends.** Store reads never initiate network traffic; stale facts stay readable with freshness metadata; only a caller-asserted freshness condition fails — with the exact `RefreshPlan` it would take — and refresh → await → read is workflow, not a fused read. Plans-as-remedies are a store-side idiom only. *Pinned:* `tools/docs-check.sh` (store ∌ HTTP), `acquisition-mcp/tests/plan_loop.rs` (offline paths raise no daemon); the asserted-freshness read has no consumer yet (`PRICING-SLICE.md`). Decided 2026-08-31.
- **C42 — v1 request budget is logical work, enforced at admission: the daemon refuses a plan before any child submission if its logical bound exceeds `max_requests`.** An actual-wire-send budget is a separate, deferred feature; the tripwire and lifetime ceiling stay what `LIVE-TESTING.md` says. *Pinned:* `daemon.rs` (admission), `acquisition-cli/tests/apply_loop.rs`. Decided 2026-08-31.
- **C43 — Apply is its own pure fan-out parent job kind (`apply`), never the `refresh` parent.** Its params carry the plan's actions as explicit `(kind, params)` child tuples; the parent performs no send of its own and submits exactly one child per tuple. What the daemon admits is **vocabulary, not meaning** — single-request kinds only — and admission is at submit, before a job id exists. *Why:* the refresh parent re-lists by construction, which contradicts "executes exactly the listed actions"; the daemon stays plan-blind. *Details:* `daemon.rs` doc, C43. *Pinned:* `acquisition-cli/tests/apply_loop.rs`. Decided 2026-09-01.
- **C44 — Apply refuses a plan whose sync-policy revision is no longer the stored one.** A plan is authorization *derived from intent at a revision*; intent edited since revokes the derivation. Checked frontend-side against a fresh read immediately before submit. **Fact drift does not refuse** — the authorization is the bounded action set, not a world-state assertion. *Why:* the CAS reasoning extended from writing intent to spending it, and replanning is free. *Details:* `acquisition-plan` doc, C44. *Pinned:* `tests/plan_json.rs`; fact drift: `acquisition-plan/src/lib.rs`. Decided 2026-09-01.
- **C76 — One door, as direction: an explicit selection (`--tabs`, `--all`, `--characters`) compiles to a plan through the same envelope and apply, and the ad-hoc `refresh` kind retires when nothing submits it.** The selection plan's precondition set is empty (no stored intent was derived from); its listing, freshness and two-cycle semantics are ruled in its own slice, with `tools/persist-check.sh` moved onto it. *Why:* two doors to one task; the empty set is the third data point for pattern 9's precondition set (policy: one; price: many; selection: none). Four tracer runs not using the old door are weak evidence about one-off workflows, so the semantics wait for their slice. Ruled 2026-09-03.
- **C77 — Freshness is evaluated at compile time against the window; a later replan that refetches facts which aged past the window during a long cycle is correct, not a fault.** A plan does not pre-fetch what is fresh at compile. Naming the facts that will age during the cycle (`aging`) belongs to a quote-bearing plan whose cycle estimate is trusted, and waits for that evidence. *Why:* the 2026-09-02 rerun's 6-request cycle 2 was the window doing its job; an offline plan has no honest cycle estimate; a cycle-based handle ("fresh as of every run") is the C++ model the policy replaced (C36). Ruled 2026-09-03.

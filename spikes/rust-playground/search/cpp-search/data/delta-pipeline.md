# What the delta-native items pipeline paid to keep search results instant

Sources, all at commit `946a4f51` (branch `master`): `docs/design/items-pipeline.md` (plan),
`docs/design/items-pipeline-m2.md` (M2 spec, frozen rev 9), `docs/design/items-pipeline-m3.md`
(M3 spec, frozen rev 4 + 3 post-freeze amendments), `docs/design/m3-sort-profile-result.md`
(S1-M3 spike), `docs/design/m2-m2-result.md` (M2-M2 checkpoint), `docs/design/m1-m3-result.md`
(M1-M3 / S3-S7 gate), `docs/design/m1-m2-result.md` (M1-M2 status burst),
`docs/design/items-pipeline-m{2,3}-reviews.md`; code `src/search.h`, `src/search.cpp`,
`src/sortkey.h`, `src/bucket.h`.

Naming: `n` = items in the collection, `d` = items in one delta, `t` = display tabs,
`runs` = contiguous row runs a delta's removals/insertions form in a sorted bucket,
`b` = items in the affected bucket (By-Tab display buckets are structurally capped at 576 =
a 24x24 quad stash). A "delta" is one fetch source's complete replacement
(`TabRefreshed(location, items)`), arriving roughly one per 20 s under GGG rate limits.

| `MatchesActiveFilters` per arrival (the surviving half of M2's intersection test) | O(d x active filters) per delta, no index — same per-item loop `FilterItems` runs, evaluated on the delta's items only | Turns "does this delta change the view?" into O(delta) instead of O(collection); lets removal/insertion be decided without a refilter | M2 D9 (intersection, O(delta items)); M3 D3 (the match half survives; the intersection *sets* `m_visible_sources`/`m_visible_sources_by_tab` and `HasVisibleSource`/`HasVisibleGhostUnder` were **deleted** by the July 31 2026 post-freeze amendment once the throttle's gate went away — they had become write-only state maintained per delta with zero readers) | `src/search.h:174-179`; `src/search.cpp:1375-1384`; call site `src/search.cpp:884-896` |

Append: O(d), order invalidated, deferred to expansion. | Lazy flat-collection (`items()`) rebuild + the two staleness marks (By-Item side / By-Tab side) | Delta maintains only the *active* mode's buckets and indexes: O(delta). `items()` rebuilds O(n) on first read; the inactive mode's buckets rebuild O(n) at the next mode switch. Hydration rule: "any operation that consumes keys ... hydrates missing keys first", an O(b) build | Retires the per-comparison regex toll (40x on cached keys, 10x even rebuilding every refilter) and bounds resident memory to one search's materialized set | M3 D1 (lever A; residency R2-3/R2-4, hydration R3-1); key residency and sorted validity are independent axes, "sorted-but-keyless is a legitimate, explicitly handled state" | `src/bucket.h:16-58,133-171`; `src/search.cpp:264-296` (`MarkBucketCollapsed`, `EvictResidentKeys`, `HydrateFlatBucketKeys`); `src/search.h:124-142` |
| Sort-on-expand / deferred sorting (lever B): per-bucket sorted-validity flag; collapsed buckets keep arrival order and sort at next expansion | Per refilter: zero sort work for collapsed buckets (probe-verified: 0 bucket sorts, 0 key builds, 0 keyed compares). | Eager flat-bucket key hydration at By-Item activation (the one carve-out from lazy) | ~46 ms at 100k / ~475 ms at 1m, paid once at activation instead of inside the first delta | "no delta ever meets a keyless flat bucket and the merge budget in rule 2 holds unconditionally" — keeps the <= 50 ms merge budget honest | M3 D1/D4 rule 1, R3-1 | `src/search.h:135-142`; `src/search.cpp:286-296`; pin `byItemActivationDecidesDirtinessFirst` |
| Materialized `ItemSortKey` (head variant + suffix) as the single ordering truth, derived from the comparator | Memory ~286 B/item accounted (`sizeof` 144 B inline + ~142 B fresh heap). **Suffix cost:** the tie-break `(PrettyName, uid, hash)` is 3 QStrings — `uid`/`hash` are CoW copies of the `Item`'s own members ("cost nothing while the item lives"); `s2` and the suffix's `PrettyName` are two identical strings, whose sharing saves ~44 MB at 1m (~1/3 of the fresh-heap term) and is "required" by D1 | Keyed sort at 12-13 ns/compare; keyed order provably equal to comparator order (`keyedOrderMatchesComparatorOrder`); D5 fixes F67 (the dead hash tie-break) so id-less ties are deterministic | M3 D1 (key shape), D5 (intended `(name, uid, hash)` order) | `src/sortkey.h:12-35` (suffix `:27`); `docs/design/m3-sort-profile-result.md` §4 |

Falls back to scanning every bucket for an "unindexed" id (a duplicate, or the empty id shared by id-less items) | Selection-as-intent: an item moving tabs mid-refresh keeps its selection through removal + later insertion, without scanning the model; also scopes the buyout repaint | M2 D9 R6-3 (global stable-identity reselection); M3 D3 "Selection is an intent, not a row" (R1-3), R2-1 (every `RefreshFinished` outcome closes the intent window) | `src/search.h:76-94,330-348`; `src/search.cpp:615-674`; pins `selectionIntentSurvivesCrossTabMoveAcrossDeltas`, `selectionIntentClearsOnTerminalFailure` |

By-Item runs it as one A' flat replace | Deletes the last reset seam: a full refresh with the window open is "N deltas plus one reconciliation"; authoritatively replaces any content a skipped delta left stale, which licenses clearing the dirty flag | M3 D3 (R1-2); S6; O(t^2) fix in S6 review round 1 | `src/search.h:216-246`; `src/search.cpp:1103-1373`; pins `noModelResetDuringRefresh`, `finalReconciliationRemovesDeletedTabs`, `finalReconciliationInsertsNewlyListedEmptyTabs` |

The ~5.4 s mid-refresh reset at 1m was "explicitly accepted for M2" | Retiring it makes the freshness bound "trivially immediate", deletes a whole class of staleness/starvation reasoning, and honours M2's hard constraint "by having no reset at all". | The buyout key effect: `InvalidateBuyoutOrder` + the batching choke point | Resolves affected buckets through the id index — O(delta + affected bucket) — but an unindexed id (duplicate, or empty id) escalates to **every bucket**. With any non-Price/Date column active, resident keys encode no buyout state and are untouched; cells still repaint unconditionally | One reorder/model update per user command or pricing pass (never per `Set`); nested batches emit only at the outermost boundary; the snapshot's 4-pass pricing sequence emits one batch | M3 D1 rule 4 + the five batching rules (R1-6, R2-5, R2-6, R3-2, R3-3, R3-4) | `src/search.h:148-156`; `src/search.cpp:308-369`; `src/bucket.h:166-171`; pins `multiSelectionBuyoutEditReordersOnce`, `pricingPassYieldsSingleModelUpdate`, `snapshotPricingSequenceEmitsOneModelBatch`, `priceCellsRepaintUnderAnySortColumn`, `priceKeysFollowBuyoutEdits` |
| Buyout cell repaint scoped to affected contiguous runs (was one spanning `dataChanged` rectangle) | Was O(span) at ~44 us/row — "invisible in By-Tab where buckets cap at 576 rows", catastrophic in By-Item under a non-buyout sort. Debounced: at most one ~10 ms pass per interval. Immediate (user-initiated) resizes supersede a pending delta resize | Removed a ~10.1 ms flat tail from every reply's whole-path measurement (10.4 ms -> 0.216 ms) | M3 S7 review round 1 finding 2 (Tom's call: "the D9 pattern at presentation scale"; width-relevance gating deliberately not added) | `m1-m3-result.md` M2-M2 addendum + S7 review round 1; pin `deltaResizeDebounceCoalescesBurst` |
| Source-keyed item storage (`SourceKeyedItems`) on **both** worker and manager, replacing the flat vector's `erase_if` | Per-reply replacement becomes one bucket swap, O(replaced + delta); reconcile/list-deletion erases walk the bucket index, O(sources) plus erased items. ## 3. Implications for a search engine over a few hundred thousand items

| Property the C++ experience pins | Evidence it rests on |
| --- | --- |
| A filter pass is O(items x active filters) with no index, and the app never indexed for search — post-M3 "refilter cost" *means* "filter-loop cost" (~0.4 s at 1m), and optimizing it was deliberately deferred for want of per-filter attribution | Numbers: filter loop 34.4 / 391.3 ms; S7 bare `FilterItems` 20.2 / 328.8 ms; M3 D6/D7 |
| Sort keys must be defined once, derived from the ordering function, and materialized — not recomputed per comparison. Per-comparison string/regex/allocation work is the single largest cost in the whole pipeline (~3/4 of every comparator call), and it is invisible until profiled: even a numeric column paid the full toll via a regex fast path | Numbers: 7x column spread, ~600-700 ns of regex per comparison, 40x cached-key sort, 0 comparator calls after M3; M3 D1, design criterion "no code path defines order twice" |
| Ordering truth must have exactly one definition, and the equivalence between the fast path and the definition must be *pinned by a test*, not argued | M3 D1 key shape derived from `Column::parts`/`PriceColumn::head`/`DateColumn::head`; pin `keyedOrderMatchesComparatorOrder`; S8 criterion 3 |
| Materialized keys cost real memory — budget them explicitly per item, and scope residency to what is actually being looked at. ~286 B/item (~266 MB at 1m) for one column's keys; residency scoped to the active search's materialized buckets keeps the default view at exactly 0 B | m3-sort-profile §4; M3 D1 residency rules (R2-3/R2-4); measured 0 B collapsed-default, 0 B background, 223.7 MB worst shape |
| Defer ordering work to visibility: pay for the order of what can be seen, and the cost becomes proportional to the visible set rather than to the corpus | Lever B numbers (15-63 ms independent of scale); sort share 0 ms of the default refilter; M3 D2 |
| Stable item ids across refreshes are load-bearing for selection and reselection — and must be *global*, not scoped to the container the item was last in, because an item legitimately moves container mid-refresh. Identity-by-pointer and identity-by-rendered-label both failed | M2 D9 R6-3 (four verified failure modes: header-text-keyed expansion orphaned by rename, `shared_ptr`-identity reselection lost on every replaced item, restore-without-save, no scroll capture); M3 R1-3 selection-as-intent; pins `selectionIntentSurvivesCrossTabMoveAcrossDeltas` |
| Stable *container* ids matter as much: buckets keyed by `(type, id)`, never by position or display name, or a moved/renamed container splits into two, files fresh items under a stale header, or two containers collide | `src/search.cpp:430-436` comment; M2 D6/R5-1; `LocationInventory::KeyFor` used everywhere in place of `ItemLocation` equality |
| Selection-as-intent needs an explicit lifetime with a close on **every** terminal outcome, including failure — otherwise a stale intent silently reselects in a later refresh | M3 R2-1; pin `selectionIntentClearsOnTerminalFailure` |
| Ids are not guaranteed unique or non-empty in the corpus: the id index needs an explicit "cannot represent this id" set and a scan fallback | `src/search.h:86-94,330-348`; `m_unindexed_visible_ids`, `m_duplicate_visible_ids`, `m_empty_id_visible_count` |
| A single flat sorted result is the structure that fights incremental update. One sorted container takes O(n + d) per update, not O(d) — "pretending a flat bucket can take O(d) updates would be designing against arithmetic". Partitioned/bucketed results, by contrast, make an update O(d + bucket) and flat across corpus size | M3 D4 and its reason; By-Item 12.9 s pre-M3 and the 1,397.9 ms -> 32.4 ms remedy; By-Tab delta 0.86 ms flat across 100k and 1m |
| Notification granularity is not the same as mutation granularity — and conflating them is how an O(n + d) algorithm silently becomes O(runs x n). The fix is mutate-once, translate-and-notify | M3 S5 miss (~10^8 element moves per delta) and remedy A'; the review's correction that "mutually unsatisfiable" was too strong: "the contract binds the model's observable answers at each notification boundary, not its physical representation" |
| Any per-item broadcast whose extent is a *span* rather than the affected set is a hidden O(span) term, harmless while containers are small and catastrophic in a flat view | The ~44 us/row spanning `dataChanged`: 43,982 ms at 1m, invisible in 576-row buckets; per-run remedy |
| Structure the corpus so removal is keyed, not scanned: four O(n) `erase_if` passes per arrival were ~99% of the reply path. Key the store by the unit the source actually delivers, on *both* sides of any lane, or one side's remedy only halves the cost | m2-m2-result: 7.38/74.93 ms -> 0.234/1.225 ms via `SourceKeyedItems`; M2 D3's "worker parity is precedent, not a bound" |
| A background result set should cost nothing per arrival: flag it stale and recompute on activation. The flag is O(1); the recompute lands on the user action that wants it | M2 D9 rule 1 + M3 R1-7; probe-verified 0 refilters at the snapshot for background searches; `itemsRefreshDefersBackgroundSearchesToActivation` |
| Delta application must be able to say "nothing visible changed" precisely, or you pay a spurious full recompute later. M2's blunt always-dirty rule was accepted for simplicity and then had to be renegotiated | M3 R1-7 and pin `appliedDeltasLeaveActiveSearchClean`; M2 D9 rule 1's own accepted-cost wording |
| Keep the fail-safe direction explicit: a delta whose application was *skipped* leaves the flag dirty, and a once-per-refresh authoritative pass clears it. Incremental maintenance needs a periodic authority to converge against | `Search::DeltaApplication::processed` (`src/search.h:181-197`); `ReconcileFinalSnapshot`'s "authoritative at the row grain ... discharges R1-7's fail-safe dirtiness" (`src/search.h:232-246`) |
| Incremental maintenance is only sound if a delta can be *re-homed*: an arrival whose container disagrees with the delta's anchor must be removed where it sits and inserted under its own key. This was reachable through the public API | M3 S6 review round 1 P3; the removal predicate became per stable key; pin `reconciliationRehomesWrongBucketRow`, verified RED first |
| Do not maintain two derived views per update: maintain the active one and mark the other stale, rebuilding lazily at the switch | `m_items_stale` / `m_flat_bucket_stale` / `m_tab_buckets_stale` (`src/search.h:369-377`); `RebuildTabBucketsFromFlat`; `items()` lazy rebuild |
| Membership predicates that flip whole-view behaviour must be stable across deltas. "Filtered" had to be redefined from "at least one item was excluded" to "any filter is active", because a single arrival could flip the snapshot definition and no bucket-scoped operation can express a whole-view change | M3 D2 rule 5 post-freeze amendment (July 31 2026); `src/search.cpp:411-419`, `src/search.h:381-385` |
| Cache invalidation for ordering needs the *complete* enumeration of mutation sources routed through one choke point, and the enumeration must be checked in review — the pricing state that feeds two columns' order had five mutation paths including a migration and a latent public `Load()` | M3 D1 rule 4 (R1-6/R2-6/R3-2); S8 criterion 4 (found and closed `BuyoutManager::Load()`) |
| Batch invalidation at command/pass scope with nesting that emits only at the outermost boundary — otherwise a multi-row edit is one reorder per row, and a 4-pass pricing sequence is four full reorders | M3 D1 batching rules R2-5/R3-3/R3-4; pins `multiSelectionBuyoutEditReordersOnce`, `snapshotPricingSequenceEmitsOneModelBatch` |
| Residency and validity are independent axes. Having the cached key and having a valid order are different facts; collapsing them leaves an unhandled state (sorted-but-keyless) that a later operation absorbs as an unbudgeted rebuild | M3 R3-1 (a keyless reactivated flat bucket would have absorbed a ~368 ms build inside a <= 50 ms delta budget); `src/bucket.h:146-149` |
| Cache eviction needs an accounting gauge that balances however the owner dies, or memory claims cannot be measured | `ResidentKeyStore` releases its share of `live_key_bytes` "on eviction, move, and destruction, so the gauge balances however a bucket dies" (`src/bucket.h:16-58`) |
| A gauge that deliberately over-estimates is not a budget: bind memory budgets at process level | S7: gauge 344.2 MB vs process-level 223.7 MB at 1m; S7 review round 1 finding 1 (a required measurement unavailable where its budget binds must count as a miss) |
| Coalescing is a throttle you can delete once per-unit work is cheap — but presentation-side work sneaks back in: retiring the throttle re-exposed a per-arrival ~10 ms column resize that the throttle had been hiding | M3 D3 (throttle retired, "freshness bound becomes trivially immediate"); the S7 debounce and the M2-M2 10.1 ms tail |
| Non-resetting single-shot debounce, not a resetting one: under steady arrivals a resetting debounce starves forever. The pattern recurred at three scales (60 s refilter, 250 ms resize, 100 ms status widget) | M2 D9 rule 2 ("that is the anti-starvation half"); M3 S7 remedy; D10/m1-m2-result |
| Budget every path with a stated number *before* implementing, attribute a miss to a component before choosing a remedy, and rerun the measurement with the remedy in place — naming a remedy is not evidence. This is what caught both real misses (M2-M2's erase passes, S5's merge) | M2 D3 (R6-6: "naming a remedy is not evidence"); M2-M2 and S5 records; M3's conditional hold-point rows per stage |
| Freeze a determinate conditional rather than an open question: "flat vector; a budget miss makes the named remedy required, not discretionary" let a spec freeze without pre-judging the measurement | M2 D3 / R5-4 / R7-3 |
| (inference) A search engine over this corpus should index the filter predicates, which is precisely the term the C++ app never attacked: after keys retired the sort, ~93% of a user-initiated refilter is an unindexed linear predicate scan | derived from the S7 attribution (20.2 / 328.8 ms of 23.6 / 282.3 ms) plus D7's explicit non-choice of a lever |
| (inference) Corpus scale here is ~10^5-10^6 items on a laptop, single-threaded, in a UI thread with a 8.3-16.7 ms frame budget; nothing in the pipeline was ever parallelised or moved off-thread except the initial cached parse. Every budget above is a single-thread synchronous number | `m1-m2-result` frame reasoning; `StartParseThread` is the only worker thread cited (m1-m3-result S0 table) |
| (inference) The arrival cadence (~1 delta / 20 s, hours-long full refresh) is what made per-delta immediacy affordable; an engine ingesting faster would need the coalescing layer M3 was able to delete | M3 D3's rationale ("a delta arrives every ~20 s per tab"); the S5 option-B rejection and the S7 burst-catch-up note (~15 replies, ~150 ms) |

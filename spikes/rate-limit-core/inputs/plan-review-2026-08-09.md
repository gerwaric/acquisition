I found several issues worth resolving before implementation. The overall direction is sound, but the scope and evidence contract are still broader and less precise than the spike question suggests.

## Findings

1. High — Legacy traffic is in scope, but its bucket model is undefined.

The brief inherits D5’s five gated endpoints and says it covers the “header-driven API regime” ([design-brief.md:499](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/design-brief.md:499)). That includes the legacy stash endpoint under D5 ([network-redesign.md:568](C:/Users/Tom/Development/GitHub/acquisition/docs/design/network-redesign.md:568)).

However:

- The proposed `RulePair { burst, sustained }` and positional 5s/60s interpretation are supported only for the four OAuth policies by N12.
- N21 explicitly says the legacy bucket resolutions are unknown ([network-ground-truth.md:365](C:/Users/Tom/Development/GitHub/acquisition/docs/design/network-ground-truth.md:365)).
- The observed legacy policy happens to contain two windows, so it would silently pass the shape check despite lacking evidence that they mean 5s/60s tiers.

Before coding, choose one:

- Restrict the spike explicitly to the four OAuth API policies; or
- Represent bucket knowledge separately from window shape, with legacy policies becoming `UnknownBucketResolution` unless externally configured.

A two-window shape must not accidentally imply known bucket resolutions.

2. High — “Zero violations” conflicts with testing 429 recovery.

Agenda item 2 suggests “zero mock-judged violations” ([design-brief.md:115](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/design-brief.md:115)), but recovery correctness and escalation are explicitly load-bearing ([design-brief.md:368](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/design-brief.md:368)). Those scenarios require the client to receive deliberately injected or exogenous 429s.

Define separate verdicts:

- `client_caused_violation_count == 0`
- Injected 429s are expected scenario stimuli
- Retry timing and escalation after an injected 429 satisfy their own assertions
- Any additional 429 generated by the mock’s counters is a failure

Without this distinction, the harness cannot give an unambiguous result.

3. High — The mock risks testing the implementation against a duplicate of itself.

The N-claims establish bucket existence and conservative padding, but do not fully specify bucket boundary alignment or the server’s exact internal counter algorithm. A client and mock using the same `ceil_to_bucket` interpretation could agree while both embody the same mistaken assumption.

Before implementing the mock, define an independent oracle:

- Explicit server bucket phase, separate from client state
- Randomized/adversarial phase offsets
- Black-box counters driven only by received wire timestamps
- No reuse of client scheduling or reconciliation functions
- Boundary cases immediately before, on, and after bucket transitions

This belongs in `scenarios.md` as part of the fidelity budget, not only in implementation notes.

4. Medium — “Single serialized gate” is ambiguous relative to cap-2 concurrency.

The spike question says “as a single serialized gate” ([design-brief.md:14](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/design-brief.md:14)), while the authoritative C++ design allows two ordinary requests in flight ([network-redesign.md:574](C:/Users/Tom/Development/GitHub/acquisition/docs/design/network-redesign.md:574)). The actor serializes decisions and state ownership, but does not serialize all network traffic.

Rewrite the question or define the term explicitly, for example:

> one serialized scheduling authority, permitting up to two concurrent ordinary requests and exclusive HEAD probes

That avoids implementing literal one-request serialization and accidentally recreating F56.

5. Medium — The actor’s request lifecycle is still missing a critical transition.

The reconciliation establishes reservations at decision time, but does not say what happens when:

- A permit is reserved but dispatch fails locally
- The HTTP future is canceled before bytes are sent
- Dispatch succeeds but no response arrives
- A dropped caller leaves a request queued versus already dispatched

The C++ design distinguishes counted, in-flight requests from stopped callers because a sent request may still affect server counters. The Rust core needs an explicit contract such as:

`Queued → Reserved → Dispatched → Observed/UnknownOutcome`

In particular, decide whether an undispatched reservation is rolled back and whether an unknown network outcome remains pessimistically counted. This should be settled in `core-design.md` before the Rust types solidify.

6. Medium — The fuse adds complexity without a clear reachable protection path.

The proposed 250 ms spacing floor limits compliant choke-point traffic to 240 requests/minute, while the fuse is proposed around 500/minute ([design-brief.md:211](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/design-brief.md:211), [design-brief.md:236](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/design-brief.md:236)). Therefore the fuse cannot trip through the normal actor path.

It protects only against a fault that bypasses or corrupts spacing—but a bypass may also bypass the fuse if both live in the same path. Before retaining it, identify the concrete failure boundary it independently guards. Otherwise, simplify the spike by:

- Keeping the 250 ms structural floor
- Keeping a directly testable 4xx tripwire
- Recording the high-volume fuse as a productization candidate

If retained, make the independence between spacing and fuse structurally testable.

7. Medium — The live validation program may overwhelm the actual spike.

The core question is whether a Rust client can make the N-claims executable under simulated burst load. The brief also introduces long-running live bucket validation, machine-readable ledgers, randomized wall-clock phases, operational safety rails, and a human-gated protocol.

That is valuable research, but it is a distinct experiment with different risk and completion criteria. Consider splitting it into:

- Core spike: mock, captures, properties, actor, conformance result
- Follow-up calibration: live assumed-bucket validation

At minimum, state whether the spike can conclude successfully without completing live validation. Currently “live contact, last” and the result’s measured-lane expectations make the terminal condition unclear.

8. Low — One required-reading path is incorrect.

The brief names `inputs/rate-limiter-design-brief.md` ([design-brief.md:41](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/design-brief.md:41)), but the file is actually [rate-limiter-design-brief.md](C:/Users/Tom/Development/GitHub/acquisition/spikes/rate-limit-core/inputs/rate-limiter-design-brief.md). Fixing this now will prevent future sessions and automation from silently skipping it.

9. Low — Capture replay needs a sanitization and fixture-longevity contract.

The plan identifies `networkcapture` as a fixture source, while N23 notes that the retained capture contains account and stash identifiers and is not committed. Clarify before fixture generation:

- Which headers and timing fields are retained
- How URLs, account identifiers, tokens, and payloads are removed
- Whether sanitized derived fixtures may be committed
- Whether fixtures preserve response order, dispatch timestamps, or both
- How their provenance is recorded without retaining secrets

Otherwise “capture replay” risks either becoming non-reproducible or leaking user data.

## Recommended simplification before starting

I would resolve four items in `scenarios.md` first:

1. Scope: four OAuth policies versus all five D5 endpoints.
2. Verdict vocabulary: client-caused violations versus injected 429s.
3. Independent mock time/bucket model.
4. Definition of “serialized gate” and its cap-2 behavior.

Then define the request lifecycle in `core-design.md`. With those settled, the remaining choices can safely emerge during implementation.

## Response to follow-up questions

My answers to the planning agent:

1. Fuse: yes, relocating it to the transport boundary satisfies the concern.

It should count actual dispatch attempts independently of scheduler reservations. The important structural conditions are:

- Every relevant HTTP send passes through that boundary.
- The counter executes immediately before handing the request to the transport.
- Scheduling/spacing logic cannot mutate or reset it.
- A fault-injection test bypasses or disables pacing while still using the transport boundary and proves the fuse halts dispatch.

Anything that bypasses that boundary is an architectural bypass of the entire client safety perimeter, not a useful failure for this spike to model. A small structural test proving there is no second transport construction/send path would complete the argument.

2. Oracle: use property-style phase sweeps for timing-sensitive scenarios.

A single randomized phase per scenario can miss boundary bugs and may make failures difficult to reproduce. Paused time makes the stronger version cheap:

- Generate an arbitrary phase in `[0, bucket_size)`.
- Record the failing seed/phase.
- Apply it to every scenario whose verdict depends on bucket expiration, padding, shrinkage, residue, or retry timing.
- Keep non-timing scenarios—parsing, malformed shapes, cancellation, queue behavior—out of the sweep.

I would not require a Cartesian expansion of every scenario against every possible phase. Property-generated phases plus explicit exact-boundary cases—just before, exactly on, and just after rollover—are sufficient.

3. Scope: a 60/60 default is acceptable as an explicit assumption, but it is not proven pessimistic for legacy traffic.

Using 60 seconds for the known 5-second OAuth tier is conservative. For the legacy policy, N14/N21 provide no upper bound on bucket resolution, so “60 seconds is pessimistic” cannot currently be derived from the N-claims. The server could theoretically use a larger bucket.

I would not necessarily refuse legacy sends. Instead:

- Represent window shape and bucket-resolution knowledge separately.
- Mark legacy resolution as `Assumed(60s)`, not `Known(60s)` or an implicit default.
- Ensure results say the legacy lane is conditional on that assumption.
- Make the assumption replaceable through internal policy configuration or later GGG evidence.
- Do not count legacy conformance toward an unconditional “honors all N-claims” verdict.

Refusal is the only strictly demonstrable choice absent an assumption, but it is probably too conservative for this spike. Explicitly conditional support preserves utility without overstating evidence.

4. Live validation: keep the protocol in this spike; move execution to a follow-up.

The protocol is a legitimate reconciliation result. It affects evidence lanes, instrumentation requirements, ledger format, and what the implementation must make observable. Removing it would lose useful design work.

I would make the terminal condition explicit:

> The spike completes when offline conformance and the result document are complete. The sanctioned live-validation protocol is a designed follow-up instrument; executing it is not required for the spike verdict.

If any live run happens during the spike, treat it as optional supplemental evidence under the already-agreed protocol—not as a hidden completion gate.
